The answer in one paragraph

The agent plane is everything between a user asking for an agent and that agent's work being visible, controllable and searchable — on this device and on the user's other devices. It is built from three repositories, three planes and one spine. puppeteer is the managed-session runtime: it runs inside fieldd, because its host contract is two methods that fieldd already implements over field-native's terminal authority, and because approvals and prompts want in-process latency. rosetta is the agent data plane: a separate rosettad process per user root, supervised by fieldd, reached the way every VibeField data plane is reached — control through fieldd, bulk and streams through a ticketed direct route. VibeField composes the two at the native session id and owns policy, custody, federation and presentation. The two upstream repositories were designed against each other before VibeField consumed either; this plane keeps both of their choices and adds only the joints.

Revisions this page describes. vibe-field b7ebb444 · puppeteer 2f5ce002 · rosetta e8d907ab. Every Built claim below was read in the code at those revisions and cites its file. A Designed claim is ruled and specified but not in code, and cites its design document and decision id. An Owed claim is named on the roadmap and not designed in detail. Nothing here states an intention in the present tense. Update 2026-09-22: the AC notes on this page (LANDED §AC) were read in the code at the AC chain's tip. The MV ownership, backend/view seams and runtime-only corrections below describe the monitor-view implementation; older revision-specific diagrams remain explicitly dated snapshots.
Two of the three repositories are machine-coupled checkouts, not registry packages. puppeteer and rosetta are unpublished, so this repository consumes them as sibling checkouts pinned by revision in siblings.lock.json: puppeteer's packages and rosetta's TypeScript client enter as link: rows in pnpm-workspace.yaml, and rosettad is built from the rosetta checkout and reaches fieldd as FIELDD_ROSETTAD_BIN. The exit is a version edit (Designed — W-D8, draft/thinking-ar-sibling-workbench.md §3).

Seams

A seam is a place where one repository's code meets another's under a named interface. For each: who owns the interface, who implements it, the file on each side, what crosses, and whether it is built. The rule that makes the triad replaceable is that every joint below is a contract, never an import of internals — puppeteer sits behind AgentHost and the monitor schema, rosetta behind a versioned protocol and a ticket door.

Two methods. spawnTerminal(spec) returns the host's routing id; automateTerminal(id, operation) submits one semantic input, ordered atomically against accepted human input, and may answer {accepted: false, reason: 'human-input-conflict'}. The adapter owns the whole launch recipe; the host composes the environment policy, finds a cell and execs.

The same file carries the half that makes a daemon host possible: HostIngress {port?, token?, onBound?} and BoundIngress {port, token}. An adapter that binds a loopback endpoint mints it ephemeral by default; a host that outlives its own process needs that endpoint pinnable and reported, so it can persist {port, token} beside the session and hand them back to attachSession after a restart. onBound fires BEFORE the process launches, which is what lets the record be durable before there is anything to lose. This is the half AR-4 implements.

Walls

The ownership law would be prose without these. Three rules in scripts/check-import-boundaries.mjs decide which package may import which sibling, and they have been enforce: true from birth; the fourth, R23 in scripts/check-agent-catalog.mjs (AC-2, 2026-09-22), holds the catalog to both pins. Their descriptions are quoted verbatim.

R20

"fieldd imports puppeteer only through its runtime door (runtime · builtin-providers · core · record) + @rosetta/protocol — never an adapter or native-observation". The rule's own comment gives the reason: "an adapter import is a product branching on a provider, and native-observation is the adapters' private half. Tests may reach further (puppeteer-testing); production may not."

R21

"field-app imports puppeteer only through its view door (core · monitor · react · views) + @rosetta/protocol — never runtime, providers, record, an adapter, or native-observation". The renderer sees the agent view and never the runtime: spawning, providers and recording are fieldd's.

R22

"no puppeteer or rosetta import outside packages/fieldd and packages/field-app (D2: the runtime lives in fieldd; A4/R10 elsewhere)". Contracts stays dependency-free, plugins see only the SDK, Electron main carries no product logic, and the spine libraries never learn what an agent is.

Two rules that are not import rules

contracts is dependency-free

packages/contracts is the zero-dependency root of the graph, imported from the renderer, from workers and from Node daemons alike. It is why the monitor mirror is a mirror and not a re-export — and why the golden fixture exists at all.

only direct imports are sibling rows

In pnpm-workspace.yaml's fenced sibling block, a package gets a link: row only if VibeField imports it directly; transitive edges resolve inside the sibling's own tree. Adapters are never rows and never imports. The lock is the authority for the current package list, including the monitor-view SDK and the browser-safe rosetta clients.

Where the walls actually run, and one thing they do not yet match. The checker is invoked by scripts/preflight.mjs — once as --self-test (it proves each rule still fires on a synthetic violation) and once as --enforce — so the walls are part of pnpm verify through pnpm preflight, its first step. pnpm check:deps is a different script (scripts/check-single-copy.mjs) and does not run them.
One package the wall admits and the lock does not name. R21's door list includes @vibecook/puppeteer-react, but siblings.lock.json has no row for it and neither does the fenced sibling block. That is correct, and the two comments explaining it were written a day apart and no longer agree. R21's own comment is the older one: it says the row "waits on the react-peer answer". pnpm-workspace.yaml's block carries the answer, dated 2026-09-13 — a link: row cannot promise its React peer resolves to this tree's copy, so the renderer's build and test configuration de-duplicate React to this tree, check:deps asserts the sibling's React version is ours, and a test renders a package component with hooks, where two Reacts would throw. That is what admitted the views package, and "the puppeteer-react contract it extends stays transitive, never a row." Read the workspace file, not the rule comment.

Data domains

Three scopes, and one principle that decides all of them: ownership by construction decides consent by construction. A root under the user's partition is that user's by construction, so it is enrolled in that user's index automatically and never appears on a roll call. A root outside it is the operating-system user's, so every VibeField user's daemon discovers it and each consents separately — isolation over de-duplication.

That user's fieldd. Session records are signed with a key in the same directory, so a same-uid file dropped into the sessions directory is set aside rather than trusted — without that, a dropped file could terminate a live PTY.

login-scoped mesh

field.agents.v1

The content-free field projection, replicated to the user's other devices through the truffle store. Content never rides it; a tap fetches through a door. That the projection is content-free is GM-D4's ruling (built at MF-1), and it is a separate decision from who may read it.

Each device's fieldd publishes its own slice. Who receives it was ruled by UA-P-D2 and built at UA-P-4: a linked desktop builds its mesh node with login_allow = [the account's login], so the provider reports as peers only nodes whose owner's login matches.

The gate is per NODE, not per store, and deliberately so — a per-store allow-list would leave the connection open to a foreign login for every other namespace. Two files carry it: packages/fieldd/src/mesh-bus.ts and packages/field-native/src/services/mesh.rs, where the scope is a build-time fact, so promoting a node from capture to linked rebuilds it rather than relabelling it.

A ruling still open on this domain. GM-D10 asks what audience field.agents.v1 may have: truffle admits by hostname prefix with no per-store authorization, so the store's readers are every node on the tailnet, and the branch, model, effort, blocker tool name and label are on that wire today. The absolute cwd was already reduced to a folder basename at no product cost. The three options and the lean are recorded in docs/DECISIONS.md; the ruling is James's.

Laws that bind the plane

These are VibeField's own laws, from draft/design-00-architecture.md, applied to the agent plane specifically. They are the reason several obvious-looking shortcuts are not taken.

EL2 — bytes never ride JSON-RPC

Control-rate JSON rides the product API; high-rate or bulk traffic rides a ticketed direct route. Applied here: terminal frames go from the floor's cell to the renderer's terminal runtime and never transit fieldd; monitor deltas coalesce to at most one frame per tick per connection; and rosetta's inline images, which are content-addressed bytes, are why the history data plane must be direct rather than proxied.

Builtframes, fold Designedthe history route

EL7 — same-uid agents are the adversary

An agent PTY is born with a clean, allow-listed environment; FIELD_* and FIELDD_* are stripped, and daemon secrets never enter an agent environment. Session records are signed, and only agent-cell PTYs are ever re-adopted. The same law is why the daemon's announcement moved into a fieldd-private directory: rosettad has no authentication, so its loopback origin is the secret, and an announcement in a shared per-user directory would be a beacon every same-uid process could read.

Tolerant reader

Inbound parsing is .passthrough() with unknown-field logging, and degraded states surface as UNAVAILABLE {service, state, progress} — honest states, never blanks. The index's readiness projects straight into that shape, so a user sees "backfilling" with progress rather than an empty History.

EL8 / EL9 — lockstep for a triad

Version moves are deliberate events, never drift. siblings.lock.json pins both sibling checkouts by revision; pnpm preflight fails on a missing checkout or a revision that is not the pin and warns on a dirty tree; pnpm siblings:pin is the upgrade act, and it gets its own ledger entry. Goldens generated from the pinned version make an upstream wire change a red gate here rather than a runtime surprise.

Lifetimes and failure domains

The two-plane law says field-native outlives fieldd outlives the shell. The agent plane adds a third ceiling and is honest about it in the interface rather than promising more than it keeps.

What Ceiling Owner

Daemon lifetime — the floor's. They die with field-native, and the interface says so.

Managed observation and control

A fieldd restart, survived by re-attaching. The resting state is the re-attach; resume-when-idle is the fallback where an adapter cannot rebind.

 puppeteer in fieldd

A typed run across the same lifetimes (AR-7)

A typed agent lives on the INTERACTIVE cell the pane already had — no agent cell is minted — so its ceiling is the pane's. Across a fieldd restart it re-attaches on its own proof (agent-typed-run.ts, typedRunProof: the signed record, the pid with the same start time, its ancestry under a listed shell) and is never replaced or ended by the re-attach; when the process leaves, the exit watch withdraws the row and the pane is a shell again. What changes across a restart lives in files the shim reads every time, never in a shell's environment; the list of our shells (terminals.json) is rewritten at every birth, exit and inventory change. Limits: a pane born before the landing is never integrated (its environment was fixed at birth); after a later fieldd adopts the floor, zsh panes restore that fieldd's ZDOTDIR and non-zsh panes get its PATH; fieldd away, a name typed in our pane waits 8 s and is refused, a version query included.

How the re-attach works, and what it costs

puppeteer's own recovery is resume-respawn, and an adapter's hook endpoint is ephemeral and baked into the launched process's environment — so after the host dies, a running agent would be posting into a void. The fix is that the host gets a say over that endpoint.

the host pins the ingress

Every birth names a creation request — puppeteer's durable claim, in fieldd's custody under the user's runs directory. The adapter reports the bound {port, token} before the process launches, and that rides in the signed session record beside the claim id.

a graceful stop releases rather than closes

A detaching dispose releases the runs without marking the claims terminal, keeps the process's staged settings file and drains the bridge so in-flight posts complete. Deleting those staged files on detach was a real defect: it lost a starting process, and after a successful re-attach the hook rail executed a script that no longer existed.

the next boot re-attaches at the next epoch

fieldd reads its signed records at the first terminal inventory and attaches by identity — same provider, claim, terminal, native id. Identity is validated before the provider takes the port. A run already managed answers unbound; a stale epoch is refused naming the claim's own epoch. Only agent-cell PTYs are candidates.

what does not re-attach becomes honest

Only one adapter attaches today; the others answer ATTACH_UNSUPPORTED and ride resume-when-idle, which respawns at a turn boundary rather than mid-turn. A row that cannot do either sits PENDING with a visible reason and a verb, never a blank and never a fake.
